## Блок Г. Перехід з ФОП Олександра на ФОП Наталії

### Г0. Мета
З дня переходу **жодної нової накладної від Олександра**. Те, що ще не
поїхало, — перестворити від Наталії одним натиском. Те, що вже їде, —
доїжджає від Олександра: статуси, гроші, відмови й повернення працюють, як
доти. Нічого не губиться, жодного руху грошей поза ядром.

### Г1. Як це працює зараз (код)
- Відправники — `contentData.ship.senders` [{id, name, phone, cityRef,
  whRef, `def`, formats}] (Налаштування → Відправка, `renderShipSettings`);
  ключ — секрет `NP_KEY_<id>` у воркерах `loomiq-np` і `loomiq-money`.
- Нова накладна бере відправника з форми картки (`o.ship.sender`), без нього
  — «за замовчуванням» (`shipSenderOf`). Відправник уже створеної накладної
  — `o.ttnSender` (друга посилка — `o.ship2.ttnSender`).
- «↻ Перестворити ТТН» (`shipTtnRemake`): нова — відправником з форми, стара
  скасовується ключем `o.ttnSender`; стара → `ttnHist` (`replaced`). Тобто
  перестворення «від іншого ФОПа» вже майже є — бракує заміни відправника у
  формі й пачки.
- Реєстр (`regMake`) уже ділить картки за `ttnSender` — по реєстру на ФОПа.
- Воркер грошей (`npPollAll`) обходить НП кожного відправника його ключем;
  накладений платіж лягає на рахунок НП того ФОПа (`npAccFor`).

### Г2. Стан відправника (нове)
- `active` — як зараз.
- **`off` «не для нових»** {`offAt`, `offBy`, `to`: код нового}: у формі
  накладної його немає; нову накладну від нього адмінка не створює
  (`ttnCreateSafe` відмовляє словами); усе для старих накладних працює.
- **Від `off` не створюється жодна ТТН ніде** (Андрій, 19.11): ні нова, ні
  «↻ Перестворити ТТН», ні друга посилка, ні «Створити ще раз» — будь-яке
  створення бере активного «за замовчуванням» (Наталію). Перевірка — в
  одному місці, у `ttnCreateSafe`, щоб жоден шлях її не обійшов.
- Видалити «×» неможливо, поки є хоч одна його накладна за 120 днів (живі,
  відмови, повернення).
- Біля такого відправника в Налаштуваннях — рядок стану: «не для нових з
  DD.MM · в дорозі N · чекаємо накладеного X ₴ · відмов на повернення P».
  Ключ тримаємо **2 місяці** після переходу (Андрій, 19.11); коли всі нулі
  — «можна вимкнути ключ», вимикає Андрій.

### Г3. Підготовка (Андрій, без коду, за день)
1. Налаштування → Відправка → «+ Відправник»: Наталія — назва, телефон,
   місто й відділення відправки, формати посилок. **Код** — один раз і
   назавжди.
2. Cloudflare → `loomiq-np` і `loomiq-money` → секрет `NP_KEY_<код>` (той
   самий ключ API з кабінету НП Наталії). `loomiq-np` перед цим —
   перерозгорнути з `main` (там повернення й захист від дублів).
3. Через ≤30 хв біля Наталії «✅ ключ працює».
4. Фінанси → рахунок «Нова пошта» для ФОП Наталії, у ньому відправник
   «Наталія» — накладений платіж її посилок ляже туди.
5. Пробна накладна на одну картку → номер, «Зебра», статус → «✕ Видалити ТТН».

### Г4. Майстер переходу (нове, власник)
Біля Олександра в Налаштування → Відправка — кнопка **«Перейти на іншого
відправника…»**. Активна, лише коли в обраного нового «✅ ключ працює».

**Крок 1. Зведення** (лише читання з памʼяті; статуси — з `npSt`):
| Група | Що це | Що зробить майстер |
|---|---|---|
| а) Без ТТН | у формі збережено Олександра (`o.ship.sender` / `o.ship2.sender`) | замінить на Наталію |
| б) ТТН створена, у НП ще не здана | `ttnSender` = Олександр, статус НП «створено» (код 1) або статусу ще немає, не передано курʼєру | перестворить від Наталії |
| в) У реєстрі Олександра, курʼєр ще не забрав | як (б), але `o.reg` є | вийме з реєстру, перестворить, позначить «потрібен новий реєстр» |
| г) Уже в НП | передано, в дорозі, прибуло | нічого — доїде від Олександра |
| ґ) Відмови й повернення | коди 102/103/108/105, `npRet` | нічого — повертаються на відділення Олександра, видно в «↩ Забрати посилки» |

Кожна група — список карток (№, отримувач, ТТН, статус), (б)–(в) — з
галочками, за замовчуванням усі. B2B і B2C — разом (відправники спільні);
друга посилка — окремим рядком.

**Крок 2. «Перейти»:**
1. Олександр → `off`, Наталія → «за замовчуванням».
2. Група (а) — лише поле відправника, через `orderApply`, по одній.
3. Групи (б)–(в) — по одній, з паузою, кнопка рахує «12 з 40»:
   - (в) спершу — воркер `registryRemove` (нове: `ScanSheet.removeDocuments`
     ключем Олександра); не вийшло — картку пропустити з причиною;
   - нова накладна від Наталії — `ttnCreateSafe` (ті самі отримувач, вага,
     формат, опис `#№`, контроль оплати = `LQMoney.codFor`; воркер
     `sameDocs` не дасть дубля при повторі);
   - **один запис у картку** через `orderApply`: нова ТТН, `ttnSender` =
     Наталія, стара → `ttnHist` {replaced, newTtn, why:'sender-switch',
     sender: Олександр, npDel:false}; `npSt`, `regFail`, `reg` зняті;
     позначка **`zebraNew`** «надрукуйте нову наклейку»;
   - лише тоді — скасування старої ключем Олександра → `npDel:true`; не
     скасувалась — «зайва» в «Стан системи» (`ttnExtraRows`, як зараз).
   - Запис не ліг — стара лишається в картці, у НП нічого не скасовано,
     рядок «не вийшло — ще раз».
4. Журнал: `accLog('sender-switch')` по картці.

**Крок 3. Звіт:** переведено (а) N, перестворено (б/в) M, не вийшло K — з
причиною й «Ще раз» (майстер можна запускати скільки завгодно: він бере
лише те, що лишилось); **«Зебра на всі нові»** — один PDF ключем Наталії;
нагадування «створіть реєстр — нові накладні ще не в реєстрі».

### Г5. Після переходу
- Плитка цеху з `zebraNew` — помаранчевим «↻ нова наклейка», доки не
  надрукують нову «Зебру» (друк знімає позначку). Інакше наклеять стару
  наклейку скасованої накладної.
- «↻ Перестворити ТТН» на будь-якій старій накладній Олександра — нова вже
  від Наталії.
- Статуси, гроші, повернення («↩ Замовити повернення» — ключем того, хто
  відправляв), «Зебра» й PDF реєстрів старих накладних — ключем Олександра.
- Рахунок НП Олександра у Фінансах лишається; Звірка (`cod_late`) стежить за
  його посилками, як доти.

### Г6. Як провести день переходу
1. Ввечері — Г3 (підготовка).
2. Зранку **до приїзду курʼєра**: майстер → «Перейти».
3. Цех: «Зебра на всі нові» → переклеїти наклейки на посилках з позначкою.
4. «Створити реєстр» — уже від Наталії.

### Г7. Перевірити до реалізації
- Чи видаляє НП накладну з реєстру без вийняття (`InternetDocument.delete`) —
  на тестовій накладній.
- Чи НП дозволяє `registryRemove` для реєстру, який уже роздруковано.

**Тест:** `tests/sender-switch.mjs` — групи зведення; `off` прибирає з
форми й не створює; (а) міняє лише відправника; (б) «спершу нова, один
запис, потім скасувати», ключі правильних ФОПів; (в) з реєстру; повторний
запуск не дублює; «×» заблоковано; `zebraNew` знімається друком.
Воркер: `registryRemove` у `tests/np-ship.mjs`.

## Блок А. «↩ Забрати посилки» в Закупівлях

### А1. Що зараз
Відмова НП — колонка «Відмова НП» в акаунта (`npref`) і в цеху (`refused`).
Повернення — лише в картці: «↩ Замовити повернення» (`npReturnOrder` →
воркер `returnOrder`, `o.npRet`), «✓ Отримали назад» (`np-ret-got`).
Закупник цього не бачить. Андрій: у виробництві відмова «не підгружається»
— перевірити на конкретному номері (можливо, статус затерто 09–11.11 —
«Стан системи» → «Знайти затерті відмови»).

### А2. Нова вкладка Закупівель
«🧾 Замовити одяг» · «📦 Склад» · **«↩ Забрати посилки · N»**
(`BUY_TAB = 'ret'`). Рядок — кожна посилка B2C/B2B (перша й друга), що у
відмові або з `npRet`, і ще не «забрали» (`npRet.got`):
- № замовлення (кнопка в картку) · ФОП-відправник;
- ТТН повернення (посилання на трекінг) і сіра оригінальна ТТН;
- стан: «прибуло — забирати» (першими, зелено) / «в дорозі» / «повернення не
  замовлено» + кнопка «↩ Замовити повернення» (той самий `npReturnOrder`);
- куди прийде (відділення відправника) і скільки днів лежить (від 5 —
  червоним: платне зберігання);
- що всередині — по позиції: мініатюра, назва, колір, розмір, штуки, мітка
  «готовий дизайн» (`u.ready`) / «індивідуальний» / «з правками» (`u.base`).

### А3. «Забрали»
Галочки → **«✓ Забрали з пошти (N)»** → по кожній посилці `npRet.got {at,
by}` через `orderApply` (кожна картка окремо; не лягло — рядок лишається з
причиною). Далі вікно розкладу позицій:
- **готовий дизайн** → «На склад готових» (блок Б) з галочкою «Стан ок»
  (пошкоджене — не на склад);
- **індивідуальний / з правками** — нікуди не оформлюється (Андрій, 19.11:
  «індивідуальні не перепродамо»), лише «забрали».
Позиція з готовим дизайном отримує `u.returned {at, by, to:'stock', ok}`.

Натискають закупник, цех, акаунт, власник. Гроші не рухаються.

**Тест:** `tests/ret-pick.mjs`.

## Блок Б. Склад готових виробів і підбір під нове замовлення

### Б1. Ключ збігу
Лише позиції з **готовим дизайном** (`u.ready`). Збіг точний:
**`ready.id` + виріб (`gid`) + колір виробу + розмір.** Колір нитки — **не
порівнюємо** (Андрій, 19.11).

### Б2. Де лежить
Вкладка «📦 Склад» → окремий блок **«Готові вироби»** (не з голим одягом).
Дані — поле `ready` у тому самому документі `designJobs/stock` (правила вже
пускають `kind:'stock'` без лічильника — нового правила не треба). Рядок:
`{id, rd, rdName, pic, gid, color, size, qty, cost, from:[{orderId, uid,
at}], at}`. Правка руками й інвентаризація — лише власник; журнал руху.

### Б3. Підбір — автоматично, менеджер може відмінити
- **Коли:** у мить фіксації позиції (`u.confirmed`) — раніше клієнт ще
  міняє розмір.
- **Що:** є збіг → резерв (`u.fromStock {at, qty, row}`), склад −qty, рух у
  журнал. Хто раніше зафіксував — того виріб.
- **Менеджеру в картці** — плашка «📦 Є на складі готових — узято зі складу,
  шити не треба» і кнопка **«Відмінити — шити нове»**: виріб повертається на
  склад, позиція йде звичайним шляхом (Андрій: «якщо ні — відміна,
  повертається назад»).
- **Позиція зі складу:** закупівля одягу її не просить (`buyNeed`), у
  вишивку й на станки не йде; у «Що шиємо» — «✅ зі складу — не шити».
- **Усі позиції зі складу** → у цеху одразу «Можна відправляти»
  (`prodAt` → `ship`); частина — решта йде як звичайно.
- Аналітика «Передано у виробництво» таку позицію не рахує; собівартість —
  `cost` з рядка складу.

**Тест:** `tests/stock-ready.mjs` (збіг і незбіг, нитка не впливає, резерв,
черговість, «Відмінити», «Можна відправляти», часткове).

## Блок В. Постачальники в Закупівлях

### В1. Що вже є (показати команді)
Розділ «Підрядники» (`contentData.suppliers`: назва, сайт, контакт, строк);
постачальник товару — картка товару → «Інформація»; Закупівлі → «Треба
замовити» вже по підрядниках, без підрядника — блок унизу (`bySup`).

### В2. Зробити
1. Довідник: + телефон, месенджер (посилання), мінімальне замовлення, як
   платимо, примітка.
2. Шапка групи в Закупівлях: «🌐 Сайт», «📞 Подзвонити» (`tel:`), «💬
   Написати», строк, примітка (`host().supplier` віддає повний запис).
3. «📋 Скопіювати замовлення для постачальника» — виріб · колір · розміри ×
   штуки, разом.
4. Постачальник заповнюється **лише в адмінці** — картка товару →
   «Інформація» (`products.supplier[gid]`); один товар — один постачальник
   (Андрій, 19.11). У Закупівлях вибору немає: у блоці «Без постачальника»
   — «впишіть постачальника в картці товару» з посиланням на неї.
5. Оформлена закупівля памʼятає постачальника (`b.sup {id, name}`).

**Тест:** `tests/buy-sup.mjs`.

## Відповіді Андрія (19.11)
- Колір нитки для складу — не порівнювати.
- Підбір зі складу — автоматично, з кнопкою «Відмінити» в менеджера.
- Відмови Олександра — повертаються на його відділення, це нормально.
  Головне — закрити Олександра для нових відправок і правильно перейти
  (майстер Г4, «перестворити всі нові ТТН завтрашнього дня»).
- Постачальник — лише в адмінці, у картці товару; один товар — один
  постачальник; Закупівлі лише показують.
- Індивідуальні повернення — не оформлюються, на склад лише готові дизайни.
- Ключ Олександра — 2 місяці; головне — жодної нової ТТН від нього, будь-яке
  перестворення — від Наталії.

Відкритих питань немає.
